1 · One month axis: a Report module that owns the months

Problem. The Report is two month lists, snapshots and spending.months, each built by its own call to monthEndsFrom; the page pairs them by index (its comment: “Both calculators give the same months”), and the Net Worth breakdown sits in the Spending module only because that's where the months were.

Solution. Move buildReport out of the HTTP module into its own Report module that builds the month axis once and hands back one list of months, each carrying its Month-End Snapshot, Spending, Earnings and Change in Net Worth; the Spending module stops taking Snapshots.

  • Locality: month alignment lives in one module
  • Interface shrinks: Spending loses snapshots
  • Leverage: page, server, made-up report share it
  • Tests hit buildReport, currently untested
  • Page stops trusting an unwritten invariant

Problem. A Breakdown's Categories and Subcategories only make sense paired by position with the rules file's Category list, so the page and “What changed” each rebuild that pairing with non-null-asserted indexes, and a reorder or a kind filter applied differently gives the wrong figure under a label with no error.

Solution. Have the Spending module hand out each Breakdown's lines already named (Category, Subcategory, Uncategorised, total) with their Transactions, so callers iterate lines instead of indexing into two lists.

  • Locality: line order decided once
  • Page drops ! index lookups
  • Delete duplicate “all Transactions” helpers
  • Tests assert lines, not index pairs

3 · Reconcile overlapping Statements in one module

Worth exploring in-process · local-substitutable (fs)
  • src/scanStatements.ts — readStatements, scanStatements, combineStatements
  • src/netWorth.ts — checkStatementsAgree
  • src/spending.ts — withoutOverlaps

Before: cross-section of where “overlap” is handled
scanStatementstags only

After: one thick band
Statements module reads, tags, checks Balances agree, counts each Transaction once → every read + reconciled Balances and Transactions
netWorth: Balances in, Snapshots out
spending: Transactions in, Breakdowns out

Problem. Knowing that Statements overlap is split between the Net Worth module (disagreeing Balances fail) and the Spending module (duplicate Transactions are dropped), so each calculator's interface quietly requires raw, unreconciled input and each test file sets up overlap cases its own way.

Solution. Deepen the Statements scan so it returns Balances already checked to agree and Transactions already counted once, alongside the per-file reads the check tool needs, so a single pass serves the page and the tool.

  • Locality: all overlap rules together
  • Calculators' interfaces get simpler input
  • Check tool reads each PDF once
  • Overlap tests move to one file
Fits ADR 0001: still a full reread every run, no cache.

4 · Each reader owns the text shape it reads

Speculative in-process
  • src/scanStatements.ts — READERS
  • src/readers/amex.ts, kroo.ts, vanguard.ts, hsbc.ts and their tests

Problem. Whether a reader wants single-spaced text is decided in the folder registry, not the reader, so three readers' real input contract lives in scanStatements.ts and their tests feed a shape the production path produces elsewhere.

Solution. Every reader takes text as extractPdfText gives it and single-spaces it itself; the registry becomes a plain folder → reader map.

  • Interface is uniform across readers
  • Tests use the real extracted layout
  • Registry stops knowing reader internals
