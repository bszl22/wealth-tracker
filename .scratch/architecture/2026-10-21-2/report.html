Strong in-process
  • src/rules.ts: checkedRule (exact names), withRule, withAddition (case-insensitive, then exact parent lookup)
  • src/matching.ts: ruleMatches, previewRule (exists only to be sent to the browser)
  • src/spending.ts: firstMatch (imported by subscriptions.ts), kind ↔ direction

Categorisation Rule module · browser-safe

first match wins "contains", ignoring case name equality + trimming is this Category new? new Category's kind kind ↔ direction unknown → RuleToSave, with a specific reason

Problem. A Categorisation Rule's invariants are spread over five modules and the page, and they already disagree: a new Category's kind is decided three ways, and "is this name already there" is exact in one place and case-insensitive in another.

Solution. One browser-safe module owns everything about a rule and the Categories it names; rules.ts shrinks to reading and writing the rules file, and spending, Subscriptions, Suggested Rules and the rule form all call the one module.

  • Locality: rule invariants in one module
  • Leverage: server and page share one interface
  • Delete matching.ts as a pass-through
  • Bad adds gets a specific error
  • Tests hit rule behaviour without DOM

Problem. The Tracker is composed twice, almost line for line, so the only composition tests reach is the made-up one; a wrong wire in main.ts, or the rules file's save queue and atomic rename, passes every test.

Solution. A Tracker module built from its adapters (Statements source, rules file store, Claude, today and whether a key is set); main.ts passes the real ones, the made-up Report passes invented ones.

  • Two adapters justify each seam
  • Locality: wiring lives in one module
  • Page tests exercise the real composition
  • Env and clock become inputs
  • Room to skip the rescan on suggest

Problem. The page tests replace the HTTP adapter with a hand-written copy of its routing, so the real one's error codes, body limits and the "scripts import only types" rule go untested.

Solution. Expose the server's request handling as a module that takes a request and gives a status and body; the page tests route fetch through it, and one test checks every served script's imports.

  • Delete the duplicated routing stub
  • Interface is the test surface
  • Browser-import rule gets a test
